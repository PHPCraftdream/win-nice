## Findings

### P2 — устанавливаемый SKILL.md по-прежнему документирует старое поведение `%`

Файлы: `skills/win-nice/SKILL.md:69-90`, `README.md:20-55`.

В `49db324` раздел README правильно обновлён: PowerShell launcher отказывается
запускать cmd fallback, если аргумент содержит `%`, печатает ошибку и возвращает
код 1. Но копируемый в Claude Code и Codex skill всё ещё говорит, что `%` может
дойти до `cmd.exe` и подвергнуться expansion.

Это особенно важно именно для skill: агент будет принимать решения по
установленному `SKILL.md`, а не обязательно читать README репозитория. В итоге он
может считать команду выполненной с потенциально изменённым аргументом, хотя она
вообще не запускается.

Рекомендация: синхронизировать `SKILL.md` с тремя случаями из README:

1. direct `.exe` path сохраняет `%`;
2. `.ps1` fail-closed отклоняет `%`, если требуется cmd fallback;
3. `.bat` entry point может повредить `%` ещё до входа в `.ps1`.

После правки добавить простой Node-тест, сравнивающий наличие ключевой
fail-closed формулировки в README и source skill, чтобы эти две пользовательские
инструкции снова не разошлись.

### P2 — новый fail-closed regression test покрывает только 7 из 10 launcher-скриптов

Файлы: `test/win-nice.Tests.ps1:440-465`, `bin/admin.ps1:140-151`,
`bin/admin.ps1:183-195`, `bin/cy.ps1:140-151`, `bin/cx.ps1:140-151`.

Таблица `$fallbackPercentTools` включает пять priority-команд, `cap` и `pint`,
но не включает `admin`, `cy` и `cx`. Во всех трёх пропущенных командах есть
собственная копия той же защитной логики. Для `cy`/`cx` fallback является
обычным сценарием на Windows, потому что npm-команды `claude` и `codex` обычно
представлены `.cmd` shim-файлами.

Нынешний test oracle также слишком слабый: он требует только, чтобы stderr
содержал символ `%`. Другая ошибка, случайно упомянувшая входной аргумент, может
удовлетворить проверку, хотя ожидаемая ветка `Refusing to run` не сработала.

Рекомендация:

- добавить `cy`/`cx` через уже существующий fake-PATH helper;
- отдельно проверить не-elevated ветку `admin` — `%` отклоняется до UAC, поэтому
  тест не должен открывать consent prompt;
- для elevated `admin` использовать отдельный ручной/elevated прогон;
- проверять стабильную часть сообщения `Refusing to run: argument contains '%'`,
  exit code 1 и отсутствие marker-файла.

Не-elevated `admin` был дополнительно проверен вручную: команда завершилась с
кодом 1 до появления UAC prompt.

## Улучшения P3

### P3 — elevated-ветка новой realtime-логики всё ещё не исполняется в CI

Файлы: `test/win-nice.Tests.ps1:181-203`, `.github/workflows/ci.yml:30-34`,
`.github/workflows/publish.yml:44-48`.

Условное ожидание `RealTime`/`High` логически исправляет прежний hardcode, но
обычный GitHub-hosted runner выполняет только не-elevated ветку. Локальный
прогон также оставил два `admin`-теста skipped. Поэтому новое ожидание
`RealTime` пока подтверждено чтением кода, а не выполнением.

Рекомендация: перед релизом выполнить и сохранить результат полного elevated
прогона. Если проекту понадобится постоянная гарантия, выделить редкий
self-hosted/manual workflow, не повышая привилегии обычных PR jobs.

### P3 — новые exit-code правила skill CLI не отражены в README

Файлы: `install/cli.js:37-47`, `README.md:221-240`.

README объясняет, что конфликтующий target будет `skipped`, но не сообщает, что
после `49db324` partial install и конфликтующий uninstall завершаются ненулевым
кодом. Это полезное и правильное изменение контракта, однако оно может удивить
скрипты, которые ранее ориентировались только на stdout.

Рекомендация: одной фразой документировать exit code 1 при любом конфликте и
exit code 0 для чистой установки/удаления либо отсутствующих targets.

### P3 — дублирование launcher-кода остаётся главным риском сопровождения

Fail-closed проверка, quoting, Win32 `CreateProcess` и обработка ошибок всё ещё
продублированы примерно в десяти `.ps1`. Неполная таблица новых тестов уже
показывает практический эффект: при изменении общей гарантии легко забыть три
реализации.

Рефакторинг необязательно делать перед ближайшим релизом. Сначала безопаснее
довести общий табличный тест до полного покрытия, а затем вынести общий launcher
в versioned helper/module отдельным изменением.
