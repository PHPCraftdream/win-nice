## Замечания

### P1 — исправление PowerShell-параметров в `cap` неполное

`cap 50 node -e 0` теперь работает, но `cap 50 node -p 0` завершается ошибкой.
Объявленный параметр `$Percent` позволяет PowerShell воспринять следующий `-p`
как сокращение `-Percent` и повторно связать уже заданный параметр.

Проблема воспроизведена на текущем коммите.

Следует полностью отказаться от блока `param(...)` и читать как процент, так и
команду из `$args`, например первый элемент как процент, а оставшиеся — как
команду и её аргументы.

Код: [`bin/cap.ps1`](../../bin/cap.ps1#L3)

### P1 — раскрытие `%VAR%` способно изменить или разделить команду

`cap.ps1` и `admin.ps1` собирают строку, которая повторно разбирается через
`cmd.exe /c`. Поэтому последовательности вида `%NAME%` раскрываются как
переменные окружения.

Проверенный пример:

```text
WIN_NICE_REVIEW_SENTINEL=VALUE&echo SECOND_COMMAND_RAN
cap 50 echo %WIN_NICE_REVIEW_SENTINEL%
```

Результат:

```text
VALUE
SECOND_COMMAND_RAN
```

Таким образом, один аргумент превращается в две команды. Для `admin` это особенно
опасное поведение, поскольку получившаяся строка запускается после UAC elevation.

Публичный интерфейс обещает передавать `<command> [args...]`, поэтому ограничение
нельзя считать только документируемой особенностью. Надёжное исправление — не
пропускать произвольные аргументы через shell-строку: запускать executable
напрямую и отдельно обрабатывать `.bat`/`.cmd`.

Код:

- [`bin/cap.ps1`](../../bin/cap.ps1#L20)
- [`bin/cap.ps1`](../../bin/cap.ps1#L136)
- [`bin/admin.ps1`](../../bin/admin.ps1#L13)
- [`bin/admin.ps1`](../../bin/admin.ps1#L26)

### P1 — `.bat`-обёртки теряют метасимволы при вызове из PowerShell

Новые тесты запускают обёртки из специально созданного `.bat`, где аргументы
заранее заключены в подходящие кавычки. Это не соответствует обычному вызову из
PowerShell.

Например:

```powershell
idle cmd /c echo 'A&B'
```

На текущем коммите выполняется сначала `A`, а затем отдельная команда `B`. Та же
проблема конструктивно присутствует в `belownormal`, `cy` и `cx`.

Для `cap` и `admin` PowerShell обычно выбирает одноимённый `.ps1`, но у
`idle`, `belownormal`, `cy` и `cx` PowerShell-версий нет.

Рекомендуется добавить `.ps1`-обёртки или заменить строковые `.bat`-прокси
единым launcher-механизмом.

Код и тест:

- [`bin/idle.bat`](../../bin/idle.bat#L8)
- [`bin/belownormal.bat`](../../bin/belownormal.bat#L8)
- [`bin/cy.bat`](../../bin/cy.bat#L4)
- [`bin/cx.bat`](../../bin/cx.bat#L4)
- [`test/win-nice.Tests.ps1`](../../test/win-nice.Tests.ps1#L54)

### P2 — release workflow публикует без Windows-интеграционных тестов

Publish workflow запускает только `npm test`. Pester-тесты, проверяющие реальные
Job Objects, priority classes и передачу аргументов, перед `npm publish` не
выполняются.

Дополнительно workflow не проверяет совпадение версии тега с `package.json`,
принимает любой тег вида `v*.*.*` и устанавливает непредсказуемый `npm@latest`.
В результате тег можно поставить на коммит с поломанным Windows-поведением и
опубликовать его без интеграционной проверки.

Рекомендуется:

- запускать Pester перед публикацией;
- проверять, что `vX.Y.Z` совпадает с версией пакета;
- использовать явно выбранную версию npm.

Workflow: [`.github/workflows/publish.yml`](../../.github/workflows/publish.yml#L23)

### P2 — тест `admin` отображается как пройденный, хотя не выполняется

На не elevated runner тест делает `return`, после чего Pester считает его
успешным. В текущем прогоне тест показан зелёным, хотя ветка запуска команды не
проверялась.

Тест следует явно помечать как skipped. Построение командной строки также стоит
вынести в отдельно тестируемую функцию, не требующую UAC.

Тест: [`test/win-nice.Tests.ps1`](../../test/win-nice.Tests.ps1#L235)

### CPU-тест не проверяет близость к заданному лимиту

Сейчас проверяется только `capped < baseline`. Существенно неправильный лимит
тоже может пройти при удачном измерении. Нужен разумный верхний порог с допуском
и условия, позволяющие корректно пропустить тест на перегруженном runner.

Тест: [`test/win-nice.Tests.ps1`](../../test/win-nice.Tests.ps1#L187)

### `status()` не валидирует структуру manifest

Синтаксически корректный JSON с отсутствующим или не-массивным `files` приведёт
к исключению при вызове `.join()`. Стоит валидировать схему manifest при чтении
или перед выводом статуса.

Код: [`install/cli.js`](../../install/cli.js#L8)
