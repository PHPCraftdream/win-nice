## Итог

**Найдено 0 P0, 0 P1, 1 P2 и 2 P3. Выпуск `0.2.0` пока не рекомендуется:
P2 оставляет заявленный hard wall-clock/sleep-safe контракт `caps` нарушенным
на реальном пути suspend/resume.**

P1 раунда 16 с уничтожением daemon на normal exit исправлен статически
последовательно во всех пяти Job Object launcher'ах. `capc` и `caps` снимают
только `KILL_ON_JOB_CLOSE`; `capt`, `capm` и `capn` повторно устанавливают свои
affinity, job-memory и active-process limits без kill-on-close bit. Cleanup
вызывается только после получения exit code непосредственно обёрнутого root;
exception/timeout paths до него не доходят и сохраняют аварийный backstop.

P2 раунда 16 уменьшен, но не закрыт полностью. Вместо одного длинного
относительного ожидания `caps` использует относительные ожидания по 1000 ms.
На Windows 8+ уже начавшийся `WaitForSingleObject` всё равно не считает время
sleep. После пробуждения wrapper не может пересчитать UTC deadline, пока этот
slice не вернётся. Поэтому он может опоздать до оставшейся части секунды, а
завершившийся в этом окне child даст `WAIT_OBJECT_0` и будет ошибочно принят как
успевший до давно прошедшего deadline.

## Findings

### P2-1: `caps` после suspend оставляет до секунды выполнения за прошедшим deadline и может вернуть success

Файлы: `bin/caps.ps1:183-186,391-420`, `README.md:218-231`,
`skills/win-nice/SKILL.md:69-77`, `CHANGELOG.md:17-30`,
`test/win-nice.Tests.ps1:2309-2348`.

`DeadlinePollSliceMs` равен 1000. На каждой итерации код сначала вычисляет
оставшееся абсолютное время, но затем блокируется в
`WaitForSingleObject(hProcess, sliceMs)`. Microsoft документирует, что начиная
с Windows 8 относительный `dwMilliseconds` не включает время, проведённое в
low-power state:
<https://learn.microsoft.com/en-us/windows/win32/api/synchapi/nf-synchapi-waitforsingleobject>.

Сценарий:

1. До deadline остаётся 900 ms, и `caps` входит в относительный wait на 900 ms.
2. Машина засыпает дольше deadline.
3. После пробуждения относительный wait продолжает оставшийся отсчёт; код ещё
   не дошёл до следующего `DateTime.UtcNow`.
4. Команда получает CPU и завершается в этом post-deadline окне.
5. Wait возвращает `WAIT_OBJECT_0`; `caps` получает exit code, снимает
   kill-on-close guard и возвращает normal result вместо 124.

Даже если child не завершается, формулировки «fires the moment it wakes» в
README и «fires immediately on wake» в SKILL/commit message неверны: задержка
составляет до остатка текущего 1000-ms slice плюс scheduler jitter. В худшем
варианте это не только задержка — команда, которая должна быть убита, проходит
как успешная и может оставить daemon живым.

Новый synthetic test вызывает `RemainingWaitMs(deadline, wake, 1000)` уже
**после** моделируемого пробуждения и получает 0. Он пропускает именно
проблемное состояние: поток всё ещё находится внутри ранее начатого
`WaitForSingleObject` и пока не может вызвать `RemainingWaitMs`. Поэтому этот
oracle зелёный при описанном дефекте.

Предпочтительное исправление — создать one-shot waitable timer с абсолютным UTC
due time и ждать process handle и timer handle вместе через
`WaitForMultipleObjects`, аккуратно определив политику для одновременной
сигнализации. Windows принимает положительный UTC-based absolute due time для
`SetWaitableTimer`; такой timer уже signaled при resume, если срок прошёл:
<https://learn.microsoft.com/en-us/windows/win32/api/synchapi/nf-synchapi-setwaitabletimer>.
Альтернатива — честно ослабить документацию до bounded polling latency и
добавить test model, который учитывает неистраченный относительный slice, но
это уже не текущий обещанный «immediate hard wall-clock» контракт.

### P3-1: daemon regression не доказывает, что resource limit продолжает действовать после закрытия wrapper handle

Файлы: `test/win-nice.Tests.ps1:2002-2100`, `bin/capc.ps1:375-404`,
`bin/capt.ps1:332-364`, `bin/capm.ps1:412-444`,
`bin/capn.ps1:366-398`, `README.md:201-216`.

Новая параметризованная regression проверяет важную половину контракта:
detached daemon остаётся жив через три секунды после normal exit wrapper'а.
Но обещание README состоит из двух частей: daemon должен выжить **и сохранить
лимит на весь срок жизни**. Test не проверяет CPU cap, affinity, memory ceiling
или active-process ceiling после закрытия wrapper handle.

Текстовый companion test ищет только вызов `SetInformationJobObject(...,
releasePtr, ...)` и строку warning. Он останется зелёным, если будущий refactor
случайно поставит `LimitFlags = 0` в `capt`, `capm` или `capn`, либо сбросит CPU
rate отдельным вызовом в `capc`. Текущие четыре сохранения limit выглядят
корректно при статическом чтении, поэтому это P3 test-coverage gap, а не
обнаруженная runtime-регрессия.

Исправление: после normal exit root проверять на оставшемся daemon фактический
эффект каждого лимита. Как минимум добавить source-struct assertions на
сохранённый flag/value для `capt`/`capm`/`capn` и отсутствие сброса CPU-rate для
`capc`; предпочтительнее — behavioral probes для affinity/process count и
доступных измерению CPU/memory сценариев.

### P3-2: новый release-guard failure path не покрыт, а warning теряет Win32 error

Файлы: `bin/capc.ps1:384-404`, `bin/capt.ps1:343-364`,
`bin/capm.ps1:423-444`, `bin/caps.ps1:471-491`,
`bin/capn.ps1:377-398`, `test/win-nice.Tests.ps1:1423-1439,1554-1566,1813-1833`.

На normal path второй вызов `SetInformationJobObject` снимает kill-on-close.
Если он возвращает false, launcher намеренно сохраняет exit code child и пишет
warning. Но fault probe имеет только общий `FailSetInfo`: он ломает первый
setup-вызов до запуска child и не умеет отказать именно на втором вызове.
Следовательно, не проверены три новые договорённости: exit code сохраняется,
warning действительно попадает в stderr, а закрытие `hJob` остаётся
fail-closed для surviving descendants.

Кроме того, warning не включает `Marshal.GetLastWin32Error()`. При редком
реальном отказе пользователь узнает последствие, но не причину, хотя все
остальные native failure branches сообщают код Win32.

Исправление: считать вызовы SetInfo и инъектировать отказ по номеру; проверить
второй вызов отдельно для всех пяти launchers. Захватить Win32 error сразу
после failed call и включить его в warning, не меняя exit code child.

## Проверка исправлений раунда 16

### P1 daemon lifecycle — закрыт статически

- Во всех пяти Job Object launchers normal path повторно вызывает
  `SetInformationJobObject` до `return` и до `finally`/`CloseHandle(hJob)`.
- `capc`: extended `LimitFlags = 0`, отдельный CPU-rate control не затрагивается.
- `capt`: повторно применяются `JOB_OBJECT_LIMIT_AFFINITY` и исходная mask.
- `capm`: повторно применяются `JOB_OBJECT_LIMIT_JOB_MEMORY` и исходный byte cap.
- `capn`: повторно применяются `JOB_OBJECT_LIMIT_ACTIVE_PROCESS` и исходный count.
- `caps`: resource limits отсутствуют, поэтому extended flags очищаются целиком.
- Timeout/exception/fault paths не достигают release block; kill-on-close
  остаётся backstop. `caps` timeout по-прежнему вызывает `TerminateJobObject`.
- Документация теперь не повторяет ошибочную предпосылку «root exit empties job».
- Behavioral daemon-survival regression добавлена для всех пяти launchers.

Microsoft рекомендует при изменении подмножества Job Object limits получить
текущую структуру, изменить её и повторно вызвать `SetInformationJobObject`:
<https://learn.microsoft.com/en-us/windows/win32/api/jobapi2/nf-jobapi2-setinformationjobobject>.
Текущий код полностью владеет исходным набором limits и явно восстанавливает
каждый установленный extended limit; отдельный CPU info class `capc` не
затрагивается. Нового current-code finding здесь не обнаружено.

### P2 sleep-safe timeout — закрыт частично

- Absolute UTC deadline и пересчёт remaining time устранили сохранение почти
  всего первоначального длинного timeout после sleep.
- Оставшийся относительный slice всё ещё сохраняется через sleep — P2-1.
- Pure arithmetic покрыта тестовым кодом, но blocked-wait semantics не покрыта.

### P3 stale comments — закрыт

Комментарии исправлены на `2 of 3 original Job-Object ones` и
`5 Job Object launchers`, что соответствует текущим `capc/capt/capm/caps/capn`.
