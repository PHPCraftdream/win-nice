# Release review: win-nice @ 1e191bc

Дата: 2026-09-02 15:00 (Europe/Berlin)

Объём: весь репозиторий на `master` (`1e191bc`), включая изменения после
релизного тега `v0.1.0` (`cd138b4`), новый `capm`, chaining, installer, npm
package, CI/publish workflows, документацию и устанавливаемый Codex skill.

## Итог

**К релизу пока не готов.** Автоматические проверки зелёные, базовая реализация
`capm` и nested Job Objects выглядит работоспособной, а прежние критичные дефекты
из review `2348602` исправлены. Но перед публикацией остаются два P1:

1. версия пакета не изменена относительно уже опубликованной `0.1.0`;
2. новая публичная возможность chaining описана неполно и местами неверно:
   CPU caps в nested jobs перемножаются, а не выбираются по правилу «меньший
   побеждает», и комбинация `cap ... capm 25% ...` сейчас вообще отказывается
   запускаться.

Рекомендуемый номер релиза — `0.2.0`: добавлены новый CLI-инструмент и новая
публичная композиционная семантика, а не только исправления.

## Findings

### P1 — пакет всё ещё имеет уже опубликованную версию 0.1.0

Файл: `package.json:3`.

Текущий registry state:

```text
npm view win-nice version dist-tags.latest --json
{
  "version": "0.1.0",
  "dist-tags.latest": "0.1.0"
}
```

При этом локальный `package.json` и `npm pack` по-прежнему создают
`win-nice@0.1.0`. npm идентифицирует публикацию парой name/version, которая
должна быть уникальной; повторно опубликовать ту же версию нельзя
([npm package.json documentation](https://docs.npmjs.com/cli/v11/configuring-npm/package-json/)).
Publish workflow дополнительно требует точного совпадения тега с этой версией
(`.github/workflows/publish.yml:23-31`), поэтому новый тег `v0.2.0` сейчас также
завершится ошибкой до публикации.

Исправление: поднять `package.json` до `0.2.0`, перенести `[Unreleased]` в
`[0.2.0] - YYYY-MM-DD`, прогнать `npm pack --dry-run`, затем создавать тег
`v0.2.0` только на проверенном commit.

### P1 — документация неверно описывает композицию nested CPU caps

Файлы: `README.md:123-128`, `CHANGELOG.md:13-15`; в
`skills/win-nice/SKILL.md` chaining вообще не описан.

README утверждает, что для nested jobs применится «whichever is more restrictive
wins». Для CPU hard caps это неверно: CPU rate дочернего job задаётся относительно
доступной CPU rate непосредственного родителя. Поэтому `cap 50 cap 50 ...` даёт
примерно 25% системного CPU, а не 50%. Это прямо описано Microsoft для
`JOBOBJECT_CPU_RATE_CONTROL_INFORMATION`
([Microsoft Learn](https://learn.microsoft.com/en-us/windows/win32/api/winnt/ns-winnt-jobobject_cpu_rate_control_information)).

CHANGELOG говорит лишь, что limits «compound», но не задаёт понятную пользователю
семантику; README не показывает chaining вообще; устанавливаемый skill не знает о
новой возможности. Для релизной функции это опасно: пользователь легко получит
вдвое более жёсткий лимит, чем ожидает.

Исправление: добавить один канонический раздел chaining в README и синхронный
краткий раздел в skill. Явно описать:

- одинаковые CPU caps перемножаются относительно родителя (`50% × 50% ≈ 25%`);
- memory ceilings/affinity/priority взаимодействуют по своим правилам, а не по
  одному универсальному «minimum wins»;
- порядок wrappers имеет значение для parsing и argument forwarding.

Добавить regression test для двух вложенных `cap`, проверяющий эффективный
предел, либо тестировать вычисленную конфигурацию через
`QueryInformationJobObject`, чтобы контракт не остался только текстом.

### P2 — задокументированный диапазон bare-decimal в capm не проверяется

Файлы: `bin/capm.ps1:17-33`, `README.md:174`,
`skills/win-nice/SKILL.md:56-60`.

Документация и usage обещают bare decimal только в диапазоне `0.01`–`1.0`, но
parser переводит в percent любую дробь `> 0` и `<= 1`. Фактическое
воспроизведение:

```text
powershell -NoProfile -File bin/capm.ps1 0.001 cmd.exe /c exit 0
exit=0
```

То есть `0.001` принимается как 0.1% RAM. Кроме того, unitless decimal больше
`1.0` остаётся на MB-ветке, хотя документация разрешает без suffix только целое
число MB. Такое значение может создать неожиданно микроскопический job limit и
уронить runtime вместо понятной ошибки validation.

Исправление: если unit отсутствует и в числе есть точка, принимать только
`0.01 <= value <= 1.0`; все остальные unitless decimals отклонять. Добавить
negative tests для `0.001`, `1.01` и `1.1`, а также boundary tests для `0.01` и
`1.0`.

### P2 — chaining с процентным capm зависит от порядка и ломается до запуска

Файлы: `bin/cap.ps1` (cmd fallback и `%` fail-closed), `bin/capm.ps1:37-44`,
`CHANGELOG.md:13-15`, `test/win-nice.Tests.ps1:852-919`.

Bare tool names — это `.bat`/cmd fallback для внешнего wrapper. Поэтому
естественная команда из новых primitives не работает:

```text
cap 50 capm 25% cmd.exe /c exit 0
Refusing to run: argument contains '%' and the target needs the cmd.exe fallback
exit=1
```

Обратный порядок (`capm 25% cap 50 ...`) или fraction (`cap ... capm 0.25 ...`)
обходит проблему. Существующие chain tests используют `capm 100%` снаружи либо
`400m`, поэтому несовместимость не обнаруживают.

Исправление перед релизом: как минимум документировать порядок wrappers и
рекомендовать fraction внутри цепочки; лучше сделать безопасный прямой dispatch
на соседний `.ps1`, не прогоняя имя managed tool через `cmd.exe`, и добавить
точный regression test для `cap 50 capm 25% ...`.

### P2 — обещание «всё рекурсивное дерево без исключений» слишком сильное

Файлы: `README.md:113-121`, `skills/win-nice/SKILL.md:40-44`.

Для обычных потомков `CreateProcess` наследование membership действительно
работает. Но документация утверждает, что *каждый* рекурсивный descendant
автоматически входит в job и единственный выход — `CREATE_BREAKAWAY_FROM_JOB`.
У Windows есть brokered creation paths: Microsoft отдельно указывает, что
процессы, созданные через WMI `Win32_Process.Create`, не ассоциируются с job
вызывающего процесса
([Job Objects, Microsoft Learn](https://learn.microsoft.com/en-us/windows/win32/procthread/job-objects)).

Исправление: заменить абсолютную формулировку на «обычные descendants, созданные
через CreateProcess» и перечислить известные исключения: explicit breakaway и
создание через внешний broker/service/WMI. Это не дефект Job Object реализации,
но сейчас публичная гарантия шире возможностей Windows.

### P2 — chain memory test не доказывает, что allocation сломал именно capm

Файл: `test/win-nice.Tests.ps1:886-914`.

Тест требует выделить единый `byte[2000 MB]` под лимитом 400 MB и ожидает любой
`FAILED:`. Но рядом нет контрольного запуска того же probe с roomy cap. На части
окружений такой массив может не выделиться сам по себе из-за address-space/CLR
ограничения или доступной памяти; тест останется зелёным даже при неработающем
outer capm.

Исправление: применить тот же oracle, что уже используется в основном capm test:
один и тот же реалистичный allocation сначала должен успешно пройти с generous
limit, затем отказать с tight limit. Более детерминированный вариант — проверить
назначенный `JobMemoryLimit` через `QueryInformationJobObject`.

### P2 — elevated admin ветки не были проверены перед релизом

Файл: `test/win-nice.Tests.ps1:921-986`.

Текущий Pester run: 119 passed, 0 failed, 3 skipped. Все три пропуска относятся к
already-elevated `admin` behavior/argument forwarding. Обычный CI runner также не
даёт интерактивного UAC/elevated console, поэтому зелёный workflow не закрывает
эту часть публичного CLI.

Исправление: до тега выполнить Pester из заранее elevated Windows PowerShell и
сохранить результат в release checklist. Для повторяемости желательно вынести
низкоуровневый elevated-launch routing/quoting в тестируемую функцию, оставив
ручному smoke test только сам переход через UAC.

### P3 — Win32 return values и unmanaged cleanup системно не проверяются

Файлы: `bin/cap.ps1:168-171,247-251`, `bin/pint.ps1:169-172,245-249`,
`bin/capm.ps1:250-253,326-330`; аналогично ожидание/exit code в остальных
launchers.

Результаты `ResumeThread`, `WaitForSingleObject` и `GetExitCodeProcess`
игнорируются. При редком API failure wrapper может зависнуть навсегда либо вернуть
default exit code 0. `AllocHGlobal`/`StructureToPtr`/`FreeHGlobal` не защищены
`try/finally`, поэтому exception между allocation и free оставит unmanaged leak;
при ошибке до resume нужно также гарантированно terminate/close suspended child.

Исправление: централизовать launcher primitive и проверять documented failure
values (`ResumeThread == 0xFFFFFFFF`, wait result, boolean exit-code call), а
native handles/pointers освобождать в `finally`/SafeHandle. Это hardening, не
наблюдаемая регрессия текущего happy path.

### P3 — release notes и package contents требуют очистки

Файлы: `CHANGELOG.md:24-42`, `package.json:24-30`, `CONTRIBUTING.md:8-13`.

- запись `0.1.0` обещает `preuninstall`, хотя проект уже объясняет, что npm >= 7
  этот lifecycle hook не вызывает, и manifest его не содержит;
- reference links `[Unreleased]`/`[0.1.0]` внизу changelog отсутствуют;
- npm tarball исключает `CHANGELOG.md` (а также governance/security docs), хотя
  это полезная часть release artifact;
- `CONTRIBUTING.md` говорит, что `npm install` «runs the test suite setup», но в
  source checkout postinstall фактически ничего не настраивает и тесты запускает
  только отдельный `npm test`.

Исправление: исправить историческую запись про `preuninstall`, добавить compare
links, включить как минимум `CHANGELOG.md` в `files`, упростить setup instruction.

### P3 — локальный tarball и CI tarball могут иметь разные line endings

Файлы: `bin/capm.bat`, `bin/capm.ps1`, `.gitattributes`.

`git ls-files --eol` показывает для новых файлов `i/lf w/lf attr/text eol=crlf`,
тогда как старые `.bat`/`.ps1` в этом checkout имеют `w/crlf`. Fresh checkout на
Windows применит CRLF, но локальный `npm pack` сейчас упакует capm с LF. Это не
ломает PowerShell, но делает проверяемый локально artifact не тождественным
artifact из publish workflow.

Исправление: renormalize/checkout новых managed files согласно
`.gitattributes`, затем pack/test именно того дерева, которое будет тегировано.
