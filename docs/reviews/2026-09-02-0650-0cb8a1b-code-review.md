## Findings

### P1 — Git Bash shims повреждают slash-prefixed аргументы через MSYS path conversion

Файлы: все extensionless `bin/<tool>`, например `bin/idle:1-5`.

Shim запускает Windows `powershell` и передаёт пользовательские аргументы как
`"$@"`. Перед вызовом Windows executable Git Bash/MSYS автоматически преобразует
POSIX-похожие аргументы в Windows paths. Поэтому обычные Windows switches `/c`,
`/d`, `/s`, `/q` и подобные доходят до `.ps1` уже изменёнными.

Воспроизведение:

```text
bash bin/idle cmd.exe /c exit 7
```

Вместо выполнения `cmd.exe /c exit 7` открылся интерактивный cmd prompt, а shim
завершился с кодом 0. То есть одновременно нарушены аргументы, blocking semantics
и propagation exit code. Именно Git Bash был главным мотивом добавления этих
файлов, поэтому проблема блокирует обещанную функцию.

Рекомендация: отключить MSYS argument conversion для пользовательского argv
(`MSYS2_ARG_CONV_EXCL='*'` или эквивалент), а путь к `.ps1` заранее отдельно
перевести через `cygpath -w`. Добавить Git Bash integration tests минимум для:

- `idle cmd.exe /c exit 7` → exit 7;
- `/c`, `/d` и Windows absolute path остаются точными аргументами;
- `%`, `&`, пробелы и пустая строка сохраняются;
- `cap`/`pint` корректно получают свой первый числовой аргумент.

### P1 — non-elevated admin больше не поддерживает cmd.exe builtins

Файл: `bin/admin.ps1:209-236`.

Новая ветка считает, что cmd fallback нужен только тогда, когда первый аргумент
буквально заканчивается на `.bat` или `.cmd`. Любой другой target сразу уходит в
`Start-Process -Verb RunAs -FilePath ...`. Но `ver`, `dir`, `echo`, `set`, `start`
и другие cmd builtins не являются файлами, поэтому direct launch невозможен.
Остальные launcher-реализации сначала пробуют `CreateProcess`, а при
`ERROR_FILE_NOT_FOUND` корректно переходят на cmd fallback; новый UAC path эту
семантику потерял.

Безопасное воспроизведение, не открывающее UAC:

```text
admin.ps1 ver
Elevation was cancelled or failed: ... The system cannot find the file specified.
EXIT=1
```

До `0cb8a1b` non-elevated ветка всегда выполнялась через cmd и builtin работал.
README при этом по-прежнему обещает fallback для cmd.exe builtins.

Рекомендация: перед UAC разрешать target через `Get-Command -CommandType
Application`. Реальный `.exe` запускать напрямую; `.bat`/`.cmd` и отсутствующий
Application считать cmd fallback (последний случай покрывает builtins). На
fallback применять существующие `%` fail-closed и `/d /s /v:off /c` правила.
Routing следует вынести в тестируемую функцию, чтобы проверять builtins без UAC.

### P2 — README и SKILL.md обещают WSL, но shims в WSL не работают

Файлы: `README.md:43-55`, `skills/win-nice/SKILL.md:99-110`, все `bin/<tool>`.

Оба документа объединяют Git Bash и WSL как поддерживаемые POSIX shells. В
Ubuntu 24.04 под WSL фактический запуск завершился так:

```text
/mnt/d/dev/win-nice/bin/idle: 5: exec: powershell: not found
```

В WSL доступен `powershell.exe`, не `powershell`. Простая замена имени также
недостаточна: Windows PowerShell не понимает переданный shim-ом путь
`/mnt/d/.../idle.ps1` к параметру `-File`. Кроме того, обычный Linux npm внутри
WSL отклонит пакет из-за `"os": ["win32"]`.

Рекомендация: либо честно ограничить таблицы и skill формулировкой «Git Bash»,
что соответствует комментариям в самих shims, либо добавить отдельную WSL
маршрутизацию через `powershell.exe` + `wslpath -w`, задокументировав, что пакет
устанавливается Windows-версией Node/npm.

### P2 — raw REG_EXPAND_SZ PATH больше не распознаёт эквивалентный install dir

Файлы: `install/paths.js:20-36`, `install/paths.js:97-108`.

Чтение raw registry value правильно сохраняет `%VAR%` и не-ASCII, но
`addToPathString`/`removeFromPathString` сравнивают raw элементы с раскрытым
`C:\Users\...\AppData\Local\win-nice\bin`. Эквивалентная запись через переменную
не совпадает:

```text
RAW=%LOCALAPPDATA%\win-nice\bin
ADD=%LOCALAPPDATA%\win-nice\bin;C:\Users\Computer\AppData\Local\win-nice\bin
REMOVE=%LOCALAPPDATA%\win-nice\bin
```

Install создаёт дубликат, а uninstall оставляет исходную dead PATH entry. Это
реалистичный сценарий для manually configured PATH и именно побочный эффект
перехода от expanded значения к raw REG_EXPAND_SZ.

Рекомендация: сохранять raw строку при записи, но для сравнения нормализовать
копию каждого элемента после case-insensitive раскрытия `%VAR%`. Добавить тесты
на `%LOCALAPPDATA%`, `%USERPROFILE%`, смешанный регистр и неизвестную переменную.

### P2 — документация неверно говорит, что Git Bash shim блокируется Restricted policy

Файлы: `README.md:290-300`, `skills/win-nice/SKILL.md:113-117`, все `bin/<tool>:5`.

README и устанавливаемый skill говорят, что `Restricted` блокирует direct `.ps1`
и Git Bash shim, а Bypass используют только `.bat`. Фактически каждый новый
extensionless shim также явно запускает:

```text
powershell -NoProfile -ExecutionPolicy Bypass -File ...
```

Default client policy поэтому мешает только bare `.ps1`, вызываемому самой
PowerShell. Рекомендация изменить оба документа одновременно; Group Policy
может по-прежнему иметь более высокий приоритет, это стоит оговорить отдельно.

## Улучшения P3

### P3 — финальная очистка Pester удаляет файлы других параллельных запусков

`test/win-nice.Tests.ps1:891-894` рекурсивно удаляет из общего `%TEMP%` все
`win-nice-pester-*` и `win-nice-fakebin-*`. Если два checkout/run работают
параллельно, первый завершившийся run удалит scripts и directories второго.

Лучше создавать один уникальный root с GUID на run, складывать все artifacts
только внутрь него и удалять ровно этот root в `finally`/`AfterAll`.

### P3 — npm test больше не является «no side effects»

README:318 сохранил подпись `fast, no side effects`, но новые registry tests
создают и удаляют `HKCU:\Software\WinNiceTest\<pid>`. Это контролируемый scratch
side effect, однако при crash ключ может остаться. Следует изменить подпись на
«isolated scratch registry key, cleaned up» и использовать GUID, а не только PID.

### P3 — .gitattributes добавлен без renormalize текущего index/worktree

`git ls-files --eol` показывает для `.bat`/`.ps1` `i/lf w/lf attr/text eol=crlf`.
Fresh GitHub checkout получит CRLF, но локальный tarball из текущего checkout
по-прежнему собирается из LF, то есть результат зависит от способа публикации.
Стоит выполнить контролируемый `git add --renormalize` отдельным коммитом и
проверить line endings содержимого tarball.
