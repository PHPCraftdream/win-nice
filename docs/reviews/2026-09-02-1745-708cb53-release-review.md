Если release policy допускает документированные P2, выпуск возможен после
elevated smoke test; предпочтительнее закрыть оба небольшими исправлениями до

## Findings

### P2 — WaitForSingleObject failure может оставить wrapped process работающим

Файлы: `bin/cap.ps1:266-272`, `bin/pint.ps1:264-270`, аналогичная новая ветка
во всех embedded C# launchers (`idle`, `belownormal`, `abovenormal`, `high`,
`realtime`, `capm`, `admin`, `cy`, `cx`).

`708cb53` правильно проверяет `WAIT_FAILED` и больше не продолжает работу с
невалидным exit code. Но error branch только закрывает handles и бросает
exception. Если wait сломался, child не обязан быть завершён: wrapper выходит
с кодом 1, а запущенная команда может продолжить работу в фоне. Для
`cap`/`pint`/`capm` закрытие job handle также не является kill, потому что job
не использует `JOB_OBJECT_LIMIT_KILL_ON_JOB_CLOSE` (и не должен использовать:
это изменило бы задокументированную lifetime-семантику daemon processes).

Это нарушает fail-closed ожидание launcher: вызывающая сторона получает
ошибку и разумно считает команду завершённой, хотя side effects могут
продолжаться.

Рекомендация: при `WAIT_FAILED` сохранить Win32 error, попытаться
`TerminateProcess`, по возможности коротко дождаться termination, затем закрыть
handles и выбросить исходную wait error. Проверить результат terminate и
добавить fault-injection unit test для этого branch. Для priority/admin/cy/cx
нужно добавить соответствующий P/Invoke либо централизовать native primitive.

### P2 — Pester suite не работает на поддерживаемых 1–2 processor системах

Файл: `test/win-nice.Tests.ps1:615-663,1039-1060`.

Несколько тестов безусловно вызывают `pint 2` и `pint 3`; новый nested-affinity
test также требует `pint 2 pint 3`. Сам launcher валидирует count относительно
`[Environment]::ProcessorCount`, README разрешает диапазон от 1, а Requirements
не требуют минимум три logical processors. На одноядерной/двухпроцессорной VM
suite падает на validation ещё до проверяемого поведения.

Текущая машина имеет 16 logical processors, поэтому проблема здесь не
проявилась. GitHub-hosted runner также обычно имеет достаточно vCPU, но локальные
VM и self-hosted runners остаются поддерживаемым сценарием.

Рекомендация:

- рассчитывать count и ожидаемую mask через `ProcessorCount`;
- обычные propagation/argument tests выполнять с `1`;
- whole-tree affinity test использовать `min(3, ProcessorCount)`;
- nested «inner wider than outer» case выполнять как `pint 1 pint 2` при
  `ProcessorCount >= 2`, а на однопроцессорной системе явно skip с причиной.

### P2 release gate — already-elevated admin остаётся непроверенным

Файл: `test/win-nice.Tests.ps1`, раздел `admin.bat`.

Текущий результат Pester: **124 passed, 0 failed, 3 skipped**. Пропущены
already-elevated execution/exit-code и argument-forwarding cases. Обычный
GitHub-hosted workflow не предоставляет интерактивный elevated session, поэтому
зелёный CI этот boundary не закрывает.

Это не найденный дефект. До тега запустить suite из заранее elevated Windows
PowerShell и сохранить итог в release checklist. UAC cancel/failure желательно
также проверить коротким ручным smoke test.

## P3 / улучшения

### P3 — native cleanup всё ещё не exception-safe на уровне всех handles

Файлы: `bin/cap.ps1:156-289`, `bin/pint.ps1:157-287`,
`bin/capm.ps1:250-390`, остальные embedded launchers.

Новый `try/finally` гарантирует `FreeHGlobal`, а известные Win32 false returns
имеют явные cleanup branches — это заметное улучшение. Но lifetime `hJob`,
`hProcess` и `hThread` по-прежнему кодируется повторяющимися ручными
`CloseHandle`. Неожиданное managed exception между acquisition и конкретным
branch (например, allocation/marshalling failure после `CreateJobObject`)
обходит часть cleanup. Поскольку PowerShell host сразу завершается, ОС обычно
вернёт ресурсы, но primitive сам по себе не обеспечивает строгую локальную
гарантию.

Рекомендация: `SafeHandle` либо единый outer `try/finally` с ownership flags.
Одновременно это уберёт десятки дублирующихся cleanup lines и снизит шанс
расхождения между 11 копиями launcher logic.

### P3 — новые native failure branches не имеют fault-injection tests

Файлы: все `bin/*.ps1`, `test/win-nice.Tests.ps1`.

Integration suite подтверждает только успешные реальные Win32 вызовы. Он не
может естественно заставить `ResumeThread`, `WaitForSingleObject` или
`GetExitCodeProcess` вернуть ошибку, поэтому именно добавленная в `708cb53`
логика не исполняется тестами.

Рекомендация: вынести минимальный C# primitive в тестируемый source/template и
инъецировать native-call adapter, либо хотя бы добавить compile-time/source
contract tests для ожидаемых failure constants и cleanup order. Предпочтителен
первый вариант; проверки строк не доказывают поведение.

### P3 — publish workflow защищён лучше CI workflow, но политики различаются

Файлы: `.github/workflows/publish.yml:27-32`,
`.github/workflows/ci.yml` setup steps.

Publish использует immutable action SHAs; CI всё ещё использует mutable
`actions/checkout@v4` и `actions/setup-node@v4`. У CI нет publish authority, так
что это не релизный blocker, но проверяемая среда CI может отличаться от
release job после перемещения major tag.

Рекомендация: синхронизировать SHA pins в обоих workflows, лучше через Renovate
или Dependabot. Для OIDC publish дополнительно полезен protected GitHub
Environment; базовые текущие требования npm Trusted Publishing (GitHub-hosted
runner, `id-token: write`, поддерживаемые Node/npm) соблюдены
([npm documentation](https://docs.npmjs.com/trusted-publishers/)).

### P3 — changelog смешивает пользовательские изменения и pre-release историю

Файл: `CHANGELOG.md:24-50`.

Раздел `0.1.1` перечисляет исправления `%`-формы `capm`, UIntPtr guard и huge
number parsing, хотя сам changelog отмечает, что эти формы/ошибки никогда не
публиковались. Это не неверно, но release notes для пользователя выглядят
шумнее: публичный diff `0.1.0 -> 0.1.1` фактически добавляет уже исправленный
`capm`, а не сначала выпускает дефекты и затем чинит их.

Рекомендация: оставить в пользовательском changelog конечное поведение и
существенный native hardening; внутреннюю pre-release историю сохранить в
commit messages/review reports. Не блокирует релиз.
