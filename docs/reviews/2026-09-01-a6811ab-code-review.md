## Findings

### P2 — README противоречит фактическому fail-closed поведению для `%`

Файлы: `README.md:20-31`, `bin/cap.ps1:205-220` и аналогичные проверки в
остальных launcher-скриптах.

README по-прежнему говорит, что на `cmd.exe /c` fallback аргумент с `%` может
дойти до `cmd.exe` и подвергнуться expansion. После `b572594` это уже не так:
launcher отказывается запускать `.bat`/`.cmd` или builtin, если любой аргумент
содержит `%`, печатает ошибку и завершает работу с кодом 1. Ручная проверка
`cap.ps1 50 npm --version '100%OFF'` подтвердила именно отказ с `EXIT=1`.

Это не косметическая неточность: пользователь может ожидать запуск команды с
риском изменения аргумента, хотя команда вообще не запустится. Более того,
текст ошибки отправляет пользователя в раздел README, который описывает другое
поведение.

Рекомендация: явно документировать три отдельных случая:

1. direct `.exe` path сохраняет `%` без изменений;
2. PowerShell launcher fail-closed отклоняет `%`, когда необходим cmd fallback;
3. `.bat`-обёртка всё ещё может повредить `%` до входа в `.ps1`.

### P2 — новая защита `%` на fallback-пути не покрыта регрессионным тестом

Файл: `test/win-nice.Tests.ps1:339-359`.

Существующие тесты проверяют `%` только на direct `.exe` path, а fallback-тест
с временным `.bat` передаёт лишь `&` и `|`. Нет теста, который требует, чтобы
`.ps1` + `.bat`/`.cmd` target + `%`:

- не запускал target;
- возвращал exit code 1;
- выдавал понятное сообщение об отказе.

Проверка особенно важна, потому что одна и та же защитная ветка продублирована
в десяти PowerShell launcher-скриптах. Ошибка или пропущенная проверка в одном
из них не будет замечена текущим набором тестов.

Рекомендация: добавить общий Pester test case для всех launcher-скриптов,
которым доступен cmd fallback, используя безвредный временный `.bat` с marker
file; отдельно подтвердить отсутствие marker file после отказа.

### P2 — `skill install` возвращает успех при отказе или частичной установке

Файлы: `install/skill.js:30-45`, `install/cli.js:37-45`,
`test/skill.test.js:79-89`.

`installSkill()` правильно не перезаписывает чужой файл и возвращает результат
`installed: false`, однако CLI игнорирует результаты. Поэтому команда выходит с
кодом 0 даже при конфликте. В воспроизведённом сценарии Claude target был
пропущен как чужой, Codex target установился, а процесс завершился с `EXIT=0`.

Для интерактивного запуска сообщение заметно, но автоматизация получает ложный
сигнал полного успеха и не может отличить полную установку от частичной.

Рекомендация: если хотя бы один обязательный target пропущен, устанавливать
ненулевой `process.exitCode` (или ввести явно документированный статус partial)
и добавить CLI-level тест exit code. Аналогично стоит определить ожидаемую
семантику для `skill uninstall` при пропущенном marked/unmarked файле.

### P2 — полный Pester-набор не может пройти из elevated PowerShell

Файл: `test/win-nice.Tests.ps1:181-203`.

Для `realtime` ожидаемое значение жёстко задано как `High`, исходя из
предположения, что test runner не elevated. Но именно elevated-запуск нужен,
чтобы выполнить два сейчас пропущенных теста `admin`. В elevated-сессии
`realtime` может получить `RealTime`, и тест приоритетов тогда упадёт до запуска
полного набора в единственном режиме, где admin-тесты не skipped.

Рекомендация: вычислять expected как `RealTime` для `$script:isAdminRunner` и
`High` иначе. Желательно прогонять elevated-вариант отдельно хотя бы перед
релизом, поскольку обычный GitHub-hosted runner эту ветку не покрывает.

## Улучшения без срочности

### P3 — launcher-код сильно продублирован

Уникальные имена C#-классов исправили реальный конфликт с `Add-Type`, но около
десяти скриптов по-прежнему содержат почти одинаковые реализации quoting,
direct/fallback запуска, `%`-проверки и обработки ошибок. Это уже привело к
необходимости синхронно менять много файлов и увеличивает риск расхождения.

Не обязательно рефакторить перед ближайшим релизом. После стабилизации API
имеет смысл вынести общий launcher в один versioned helper/module, сохранив в
отдельных командах только priority/job/affinity policy. До этого общий
табличный Pester-набор даст большую часть нужной защиты с меньшим риском.
