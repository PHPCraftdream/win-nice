## Findings

### P2 — capm печатает внутреннюю PowerShell-ошибку для очень большого числа

Файл: `bin/capm.ps1:25-45`, особенно преобразование в `double` на строке 29.

Regex допускает число произвольной длины, а `[double]$Matches['num']`
выполняется до защищённого `try` на строках 357-371. Поэтому malformed/out-of-
range input сначала выдаёт raw `InvalidCastFromStringToDoubleOrSingle`, включая
путь и строку исходника, и только затем обычный usage:

```text
$huge = ('9' * 400) + 'g'
powershell -NoProfile -File bin/capm.ps1 $huge cmd.exe /c exit 0
Cannot convert value "999..." to type "System.Double" ...
At D:\dev\win-nice\bin\capm.ps1:29 char:1
usage: capm <size> <command> ...
exit=1
```

Exit code безопасный (`1`), команда не запускается, но обещание clean validation
из release commit не соблюдается, а внутренности установки попадают в stderr.

Исправление: разбирать число через `Double.TryParse` с
`CultureInfo.InvariantCulture`/`NumberStyles.Float`, проверять `IsNaN` и
`IsInfinity`, а любую неудачу сводить к единственному контролируемому
`capm: <size> is out of range` без PowerShell conversion error. Добавить тест на
сотни цифр для `m`, `g` и bare-percent формы.

### P2 — nested capm ceilings описаны как точный minimum, хотя accounting scopes различаются

Файлы: `README.md:250-252`, `CHANGELOG.md:14-19`,
`skills/win-nice/SKILL.md:86-92`.

Документация говорит, что два memory ceilings дают эффективный минимум
номинальных лимитов. Это слишком сильная модель. Каждый job считает committed
memory своих процессов **и всех child jobs**; parent дополнительно учитывает
свои outer-wrapper процессы, которых нет в accounting child job. Поэтому при
`capm 500m capm 400m ...` parent может закончить budget первым из-за памяти
внешнего wrapper, даже несмотря на больший номинальный limit. Microsoft именно
так определяет aggregated resource accounting для nested jobs
([Nested Jobs — Resource Accounting](https://learn.microsoft.com/en-us/windows/win32/procthread/nested-jobs)).

Код применяет независимые Job Objects корректно; проблема в публичном
объяснении. Исправление: написать, что каждый ceiling применяется независимо к
своему accounting scope; parent включает весь child subtree плюс собственные
процессы, поэтому доступная innermost workload память не обязана равняться
`min(limit1, limit2)`. Добавить тест/пример с двумя `capm` либо не обещать
точный effective minimum.

### P2 — publish workflow не имеет общего timeout

Файлы: `.github/workflows/publish.yml:12-14`, для сравнения
`.github/workflows/ci.yml:11-15`.

Обычный CI ограничен `timeout-minutes: 20`, а tag-triggered publish job — нет.
При зависшем native launcher/Pester probe релизный job может занимать runner до
GitHub default timeout и долго оставаться в неопределённом состоянии. Это
особенно актуально, пока сами launchers используют бесконечный
`WaitForSingleObject(..., INFINITE)`.

Исправление: добавить `timeout-minutes: 20` в publish job. Желательно также
поставить timeout на `npm publish` step/добавить concurrency, чтобы повторный
tag workflow не конкурировал с уже запущенным релизом.

### P2 — три already-elevated admin сценария не покрыты текущим release run

Файл: `test/win-nice.Tests.ps1:1021-1086`.

Pester завершился `120 passed / 0 failed / 3 skipped`. Пропущены случаи,
требующие заранее elevated runner: inline execution/exit-code propagation и
argument forwarding already-elevated `admin`. GitHub-hosted CI также не
предоставляет интерактивный elevated/UAC session, поэтому зелёный workflow не
закрывает эту часть публичного CLI.

Это не найденный дефект, а release-validation gap. До тега выполнить suite из
elevated Windows PowerShell и сохранить результат. Долгосрочно — вынести больше
elevated branch logic в тестируемый без UAC primitive, оставив ручному smoke
test только сам elevation boundary.

## P3 / улучшения

### P3 — native launcher error paths всё ещё игнорируют return values

Файлы: `bin/cap.ps1:247-251`, `bin/pint.ps1:245-249`,
`bin/capm.ps1:338-342`; ожидание/exit-code аналогично во всех остальных
embedded C# launchers.

Не проверяются результаты `ResumeThread`, `WaitForSingleObject` и
`GetExitCodeProcess`. При редком Win32 failure процесс может остаться suspended,
wrapper — ждать бесконечно, либо вернуть default `0`. В `cap`/`pint`/`capm`
`AllocHGlobal` и `FreeHGlobal` не связаны `try/finally`.

Рекомендация: общий launcher primitive, проверки documented failure values,
`SafeHandle`/`finally`, terminate suspended child при ошибке до resume. Это не
регрессия happy path и не блокирует `0.1.1`, но устраняет системный класс
необработанных ошибок.

### P3 — admin ошибочно назван «elevated equivalent of idle»

Файлы: `README.md:278-282`, `skills/win-nice/SKILL.md:95-100`.

`admin` не устанавливает `IDLE_PRIORITY_CLASS`; он только повышает privileges,
ждёт завершения и передаёт exit code. Фраза может заставить пользователя
ожидать одновременно elevation и снижение priority.

Рекомендация: заменить на «blocking elevation wrapper with the same wait and
exit-code propagation semantics as the other wrappers» или просто убрать
сравнение с `idle`.

### P3 — uiup обещает результат, который не может гарантировать

Файлы: `README.md:264-276`, `skills/win-nice/SKILL.md:100-105`.

Фраза «so the desktop stays responsive» звучит как гарантия. На практике
повышение priority выбранных процессов может помочь, но не гарантирует
responsiveness при memory pressure, I/O saturation, driver/GPU stalls или
realtime workload.

Рекомендация: заменить на «intended to improve desktop responsiveness» и
кратко указать, что это best-effort one-shot tweak.

### P3 — release workflow стоит усилить по supply-chain принципу

Файл: `.github/workflows/publish.yml:8-21`.

Базовая OIDC-конфигурация корректна: GitHub-hosted runner, `id-token: write`,
Node 24, npm `11.5.1`, provenance. Она соответствует требованиям npm Trusted
Publishing
([официальная документация npm](https://docs.npmjs.com/trusted-publishers/)).
Но `actions/checkout@v4` и `actions/setup-node@v4` закреплены только mutable
major tags, а publish job не использует protected GitHub Environment.

Рекомендация: закрепить actions по commit SHA и привязать Trusted Publisher к
release environment с approval/protection rules. Это defense in depth, не
функциональный blocker.

### P3 — nested affinity можно документировать точнее

Файл: `README.md:256-259`.

README честно говорит, что nested `pint` не проверен. Microsoft при этом
относит affinity к effective limits parent chain: child может быть строже, но
не менее строгим, чем parent
([Nested Jobs — Job Limits](https://learn.microsoft.com/en-us/windows/win32/procthread/nested-jobs)).

Рекомендация: добавить integration test двух `pint` с разными masks/counts и
после него заменить «test your own combination» на установленную контрактом
семантику. Для `0.1.1` текущая осторожная формулировка допустима.
