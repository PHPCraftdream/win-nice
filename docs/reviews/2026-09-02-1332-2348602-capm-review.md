# Ревью `capm` — коммит `2348602`

Дата: 2026-09-02 13:32 (Europe/Berlin)

## Область ревью

Проверен новый инструмент `capm` из коммита:

- `2348602 Add capm: hard memory limit via Job Objects, plus open-source governance docs`

Основной фокус: `bin/capm.ps1`, три shell entry point, тесты, установка,
публикация npm, README, changelog и reference skill. Несвязанные governance-файлы
не рассматривались подробно.

## Итог

Основной Win32-механизм реализован правильно: процесс создаётся suspended,
помещается в Job Object с `JOB_OBJECT_LIMIT_JOB_MEMORY` и только затем
возобновляется. Лимит применяется к суммарной committed memory всех процессов
job'а, а не к working set или отдельному процессу. Это соответствует
[документации Microsoft по `JOBOBJECT_EXTENDED_LIMIT_INFORMATION`](https://learn.microsoft.com/en-us/windows/win32/api/winnt/ns-winnt-jobobject_extended_limit_information)
и [`JOB_OBJECT_LIMIT_JOB_MEMORY`](https://learn.microsoft.com/en-us/windows/win32/api/winnt/ns-winnt-jobobject_basic_limit_information).

P0-дефектов не найдено. Перед публикацией следует исправить один P1-блокер:
новая функциональность всё ещё имеет уже опубликованный номер версии `0.1.0`.
Также найдены четыре P2 и два P3 замечания.

## Findings

### P1 — `capm` нельзя опубликовать с текущим номером версии

Файл: `package.json:3`.

В `package.json` осталась версия `0.1.0`; этот же номер уже опубликован в npm и
помечен git-тегом `v0.1.0` на коммите `cd138b4`. `npm view win-nice version`
возвращает `0.1.0`. Реестр npm не позволяет повторно опубликовать тот же
`name@version`, поэтому текущий publish workflow завершится ошибкой, а `capm`
не попадёт пользователям.

Рекомендация: оформить feature release, например `0.2.0`, синхронизировать
`package.json`/lock-файл, перенести соответствующие записи changelog из
`Unreleased` в секцию версии и создать тег только после успешных CI/publish.

### P2 — лимиты больше 4 GiB и большинство `%`-лимитов не работают в 32-битном PowerShell

Файлы: `bin/capm.ps1:103-110`, `bin/capm.ps1:233-240`,
`bin/capm.ps1:335-344`, `README.md:169-181`.

Win32 `SIZE_T` представлен как `UIntPtr`, поэтому его ширина совпадает с
разрядностью процесса PowerShell. Парсер принимает `5g` и `25%` независимо от
архитектуры, но в 32-битном Windows PowerShell преобразование в `UIntPtr`
переполняется.

Воспроизведение через
`%WINDIR%\SysWOW64\WindowsPowerShell\v1.0\powershell.exe`:

```text
capm.ps1 100m cmd.exe /c exit 0  -> exit 0
capm.ps1 5g   cmd.exe /c exit 0  -> Arithmetic operation resulted in an overflow, exit 1
capm.ps1 25%  cmd.exe /c exit 0  -> Arithmetic operation resulted in an overflow, exit 1
```

На 64-битной машине `25%` обычно уже превышает 4 GiB. Более того, `.bat`
запускает просто `powershell`; из 32-битного родительского процесса filesystem
redirection может выбрать именно 32-битный executable.

Рекомендация: либо явно требовать 64-битный PowerShell и в `.bat` выбирать
64-битный host через `Sysnative` при необходимости, либо валидировать значение
против `[UIntPtr]::MaxValue` и выдавать понятную архитектурную ошибку до P/Invoke.
Добавить x86 regression test, если x86 остаётся поддерживаемым режимом.

### P2 — README ошибочно утверждает, что сам суффикс `%` ломается в `capm.bat`

Файлы: `README.md:62-72`, `bin/capm.bat:3-11`.

Документация приводит `capm 20% ...` как пример команды, которая якобы
повреждается batch expansion. Это противоречит как тесту
`test/win-nice.Tests.ps1:689-700`, где `50%` проходит именно через
`capm.bat`, так и ручной проверке из настоящего cmd.exe:

```text
bin\capm.bat 50% cmd.exe /c exit 6  -> exit 6
bin\capm.bat 20% cmd.exe /c exit 5  -> exit 5
```

Проблемны определённые `%...%`/`%x` последовательности в последующих
аргументах, но одиночный завершающий `%` в size token сохраняется. Сейчас
README без причины объявляет один из четырёх публичных форматов недоступным в
cmd.exe и противоречит собственному тесту.

Рекомендация: убрать специальное предупреждение про `<size>`, оставить общую
оговорку для пользовательских аргументов и закрепить `20%` отдельным cmd.exe
integration test.

### P2 — memory enforcement test не доказывает сформулированный контракт

Файл: `test/win-nice.Tests.ps1:742-768`.

Название теста говорит, что generous/tight cap проверяются на одной 200 MB
аллокации. Фактически tight-ветка запрашивает 2000 MB под лимитом 100 MB, а
roomy-ветка — 200 MB под лимитом `100%`. Поэтому тест может пройти при ошибке в
коэффициенте единиц или на независимом от Job Object отказе почти 2-гигабайтной
.NET-аллокации. Он также смешивает проверку enforcement с проверкой
`GlobalMemoryStatusEx`.

Рекомендация: использовать одинаковую умеренную аллокацию для обеих веток,
например 200 MB при заведомо достаточном и недостаточном лимите с учётом
измеренного startup footprint. Проверку `%` вынести отдельно и подтвердить
вычисленный byte limit через небольшой тестируемый conversion helper.

### P2 — `npm test` принимает WSL `bash.exe` за Git Bash и падает

Файл: `test/gitbash-shims.test.js:18-32`.

Проверка `bash -c "echo ok"` определяет наличие любого bash, хотя тесты требуют
именно Git Bash/MSYS. В текущем окружении команда разрешилась в WSL bash:
Node suite получил 7 failures из 54, включая новый `capm` test, с ошибками
`D:/dev/win-nice/bin/capm: No such file or directory` и
`powershell: not found`. Это не дефект `capm` shim, но делает общий `npm test`
красным в валидной Windows-конфигурации и создаёт ложный сигнал регрессии.

Рекомендация: определить MSYS/Git Bash по `uname -s` (`MINGW*`/`MSYS*`) и
наличию `cygpath`, либо найти `git.exe` и запускать sibling `bash.exe` по
явному пути. WSL должен приводить к skip, а не к запуску этих тестов.

### P3 — числовая валидация принимает значения, которые нельзя выразить в байтах

Файл: `bin/capm.ps1:16-25`, `bin/capm.ps1:335-344`.

Например, `0.0000001m` проходит regex и проверку `> 0`, после чего округляется
к нулю байт и доходит до Win32 с невалидным limit. Огромные десятичные строки
сначала преобразуются через `[double]`, теряя точность либо переполняясь, и
завершаются несогласованными runtime-ошибками вместо usage validation.

Рекомендация: разбирать число как `decimal`, в checked-режиме переводить в
целое число байт и проверять диапазон `1..UIntPtr.MaxValue` до `Add-Type`/Win32.
Тестами покрыть sub-byte input, максимум и значение на один байт выше него.

### P3 — тесты не проверяют фактическое значение установленного лимита

Файлы: `bin/capm.ps1:233-245`, `test/win-nice.Tests.ps1:668-804`.

Тесты проверяют accept/reject и грубый allocation outcome, но не читают job
configuration обратно. Ошибка в выборе флага, структуре или коэффициенте может
маскироваться поведением runtime/машины.

Рекомендация: добавить test hook или probe с `QueryInformationJobObject` и
проверить `LimitFlags` и `JobMemoryLimit` для `512`, `0.5g` и `%`. Это особенно
полезно для проверки layout `SIZE_T` на x86/x64.
