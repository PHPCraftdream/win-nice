## Session summary
win-nice is a Windows `nice`/`renice`/`cpulimit`-style npm package: `.bat`+`.ps1` tool pairs that wrap a command and run it under a modified priority/CPU-quota/affinity, built for running parallel AI coding agents without freezing the desktop. The session started by reviewing `docs/reviews/2026-09-01-code-review.md` (found via `/repo-sight`-style read of the existing repo) and fixing its findings in `cap.ps1`/`install/uninstall.js`: cmd.exe metacharacter injection (`&`-splitting a command in two), PowerShell common-parameter ambiguity swallowing flags like `-e`, manifest path-traversal in uninstall, and the managed-file uninstall contract vs. README. Then added GitHub Actions CI (Node 18/20/22/24 matrix) and a tag-triggered npm-publish workflow (OIDC trusted publishing, version-tag check, pinned npm). Then added new tools on user request: `admin` (elevated `idle`), `cy`/`cx` (launchers for `claude --dangerously-skip-permissions` / `codex --dangerously-bypass-approvals-and-sandbox`), `pint` (CPU affinity, "pin threads"), and `abovenormal`/`high`/`realtime` (the remaining Windows priority classes) — each as a `.bat`+`.ps1` pair using a hand-rolled C# `CreateProcess` launcher (Job Object for `cap`/`pint`, plain creation flags for the priority tools). A surprise auto-generated review of commit `f001508` (apparently a post-commit hook, not invoked by the agent) then surfaced real P1 bugs, all verified empirically before fixing: (1) declared PowerShell params ambiguously prefix-matched flags like `-p`/`-c` even without `[Parameter()]` — fixed by reading everything from `$args`, no `param()` block at all; (2) `.bat` wrappers lose metacharacters when invoked from an actual PowerShell session (not cmd.exe) — gave every priority/launcher tool its own `.ps1` (PowerShell prefers `.ps1` for bare-name resolution); (3) a deeper, unfixable-from-inside-a-.bat discovery: a literal `%` in any argument is corrupted the instant a `.bat` reads `%1`/`%*`, confirmed with nothing more than a bare `echo %1` — documented prominently, not solved. Rebuilt `cap`/`admin`/`pint`/all seven priority-class tools around a "try `CreateProcess` directly first (fully immune to cmd.exe operators and `%`), fall back to `cmd.exe /c` only for `.bat`/`.cmd` targets" pattern, discovering along the way that raw `CreateProcess` on a `.bat`/`.cmd` target silently re-invokes it through cmd.exe using unescaped text instead of failing (worked around by detecting the extension upfront). Added a `/win-nice` Claude Code + Codex skill (`skills/win-nice/SKILL.md`, cross-agent SKILL.md format) with `win-nice skill install|uninstall` copying it into `~/.claude/skills/` and (initially, wrongly) `~/.codex/skills/`. A second review of that commit found and the agent fixed: the Codex skill path was actually wrong (should be `~/.agents/skills`, re-verified against current docs), the marker comment preceding the YAML frontmatter broke SKILL.md parsing (moved after the closing `---`), skill install unconditionally overwrote existing files (now checks for the marker before overwriting), and — reproduced empirically — bare-name invocation of two different `.ps1` tools in one PowerShell session hit an `Add-Type` "type already exists" conflict because they all shared the class name `Launcher` (fixed with unique per-tool class names, e.g. `IdleLauncher`; a full shared-module extraction was considered and explicitly rejected as more refactor risk than the bug needs). Also added a fail-closed check: the `cmd.exe` fallback path now refuses to run (clear error, matching exit code) if any argument contains `%`, instead of silently risking corruption. While implementing that, discovered two more bugs unprompted: every tool's uncaught C# exception resulted in exit code 0 (PowerShell doesn't set a nonzero exit code for an unhandled `MethodInvocationException` by default) — fixed with try/catch+`exit 1` in all 10 tools; and the user's complaint about `.bat` windows popping up during test runs traced to 3 Pester tests using `Start-Process cmd ... -PassThru` without window suppression (an earlier attempt to fix this via `CREATE_NO_WINDOW` in the C# launchers was tried, found to silently swallow child stdout in the session's console-less bash context, and reverted — fixed at the actual source instead with `-WindowStyle Hidden`). Also fixed a real CPU-cap test flake exposed by a heavily loaded test machine (baseline as low as 37% with no cap at all) by switching from absolute to relative/retrying thresholds. Two commits landed this session: `f001508` (review fixes + pint/priority tools/skill) and `b572594` (second-review fixes: skill path, type collision, fail-closed `%`, exit-code bug, window-popping bug, CPU test flake). ## Decisions
- Chose per-tool unique C# class names (`IdleLauncher`, `HighLauncher`, ...) over extracting a shared launcher module, to fix the `Add-Type` type-collision bug — smaller, independently-verifiable change; explicitly rejected the shared-module refactor as more risk than the bug warranted under time pressure.
- Chose `-WindowStyle Hidden` on the Pester suite's `Start-Process cmd ...` calls over `CREATE_NO_WINDOW` in the C# launchers — the latter was tested and found to silently discard child stdout when there's no real console to inherit (the session's own bash-driven invocation context), which would be a worse regression (silent output loss) than the cosmetic window-popping it was meant to fix.
- Chose NOT to add checksum-based edit detection to skill install/uninstall (reviewer suggested it) — marker-comment presence is deliberately consistent with the already-established bin/ installer contract ("managed files replaced regardless of edits"); the actual reported bug was install having zero existence/ownership check at all, which is now fixed.
- Chose not to redesign Codex skill distribution as a "plugin" (OpenAI's now-recommended distribution mechanism) — noted as a known tradeoff, out of scope for this session.
- Chose relative/retrying thresholds for the Pester CPU-cap test over a fixed absolute one, after confirming via direct measurement that the test machine can be too loaded for an uncapped baseline to exceed even a modest cap target.
